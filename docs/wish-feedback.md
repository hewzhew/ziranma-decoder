# “向猫猫许愿”与“猫猫应愿”：本地反馈和整理

## 目标

用户遇到候选、排序、闪烁、延迟、输入模式或兼容性问题时，应能用一次明确动作
留下自己的说明，并把问题发生前后的输入法内部现场绑定到同一个本地反馈包。
反馈首先服务于本人和本地开发，不是遥测系统，也不自动上传 GitHub 或任何服务。

当前 Alpha 在每个前台文本服务中维护严格有界的滚动内存现场：候选展示、选择、
提交、取消和上下文资格都会经过输入法自身记录。默认情况下，没有明确许愿就不写
文件，应用退出即丢失；用户还可以另行一次性开启
[持续研究收件箱](research-feedback.md)，把普通输入域里的同类事件写入独立的本地
加密批次。“许愿”仍只标记值得优先处理的短时现场；“应愿”再负责本地查看、整理
和可审阅导出，而不是另建全局键盘钩子或读取宿主周围正文。

## 参考模式

成熟反馈工具的共同点不是“尽量多收”，而是把用户描述与可选择的现场证据绑定：

- Windows Feedback Hub 允许先写问题或建议，再选择附件、截图以及
  “Recreate my problem”；`Win+F` 还能先带着现场打开入口，未完成内容保留为草稿；
  录制前再选择包含哪些诊断数据；
- VS Code Issue Reporter 把问题类型、标题和描述放在首位，并把系统信息与扩展
  信息作为可见复选项；附加信息可由用户查看或下载；
- Sentry User Feedback 可以在没有异常事件时由用户主动打开；与 Session Replay
  结合时，会在打开反馈入口前保留最多约 30 秒的短时缓冲；Breadcrumbs 则用
  类型、类别、级别、时间和键值数据组成结构化事件轨迹。
- Apple Feedback Assistant 强调尽快保留具有时效性的现场，同时允许先保存，
  再切换设备补充细节和提交；提交后以记录状态继续管理。

这些设计不能原样照搬：本项目处理真实输入文字，默认边界应比通用应用反馈更
严格。可借鉴的是“主动入口、短时前情、分层授权、提交前可见”，不是其联网
后端。

## 推荐交互

控制入口不注册新的全局快捷键。语言栏菜单若被宿主显示可以继续使用；日用路径
明确拆成“输入法内捕获”和“独立管理器整理”：

1. 前台文本服务启动时建立有界滚动内存现场；默认不写文件，宿主退出即消失；
2. 输入法内 `xuy + Tab` 直接冻结最近完成的输入片段与少量前文；近 30 秒兜底
   继续留在语言栏或管理命令中；保存后只显示短暂回执，不切走焦点或打开窗口；
3. 按需打开的“猫猫应愿”按时间列出本地许愿，默认只展示每条记录的重点片段；
4. 用户可展开前后记录，并补充或修改类别与说明；这些整理信息和原始现场分别
   加密，原始现场保持不可修改；
5. 关闭管理器即退出，不驻留托盘，也不影响输入法继续维护下一次滚动现场；
6. 可恢复删除、处理状态、重要标记和脱敏导出继续按独立步骤增加，不与捕获动作
   混成一次授权。

`wishpad` 现在是单实例的“猫猫应愿”管理器。它不再通过 TSF 通道发起捕获，
也不再只猜测“最近一条”：左侧选择明确记录，右侧才解密并显示重点现场；整理
窗口绑定选中的不可变 ID。类别和说明可以反复修改，每次替换都只把 DPAPI 密文
写入临时文件并原子发布。管理器不会顺带扫描其他私人会话。

输入法内另有一个严格限域的助记入口：只有组合码精确等于 `xuy` 后按 `Tab` 才
立即保存；普通 `xuy + 空格` 继续输入文字，其他码的 `Tab` 继续走找字辅助。
类别、重要性和文字说明不要求打字时决定，而是留给之后审阅。若开发测试宿主没有
维护滚动现场，入口才显示一次明确的“开始反馈”确认，不会伪装成已经保存。
保存完成后用不抢焦点的短暂回执明确显示结果；成功捕获时配合小幅“捧住愿望”猫
图示，立即出现并在 1.2 秒后直接隐藏，不使用渐入、弹跳或透明度更新。失败回执保留
纯文字，避免用成功图示掩盖异常。

## 当前实现

当前实现先完成一条只传无正文控制字的安全短链路：

1. 每个前台文本服务默认维护有界滚动内存现场，并保留密码、私密和未知输入域的
   fail-closed 上下文资格门；许愿与持续研究分别控制两个本地加密目录，持续研究
   默认关闭；
2. `xuy + Tab` 用最近三次已完成输入确认存在可用重点，把最后一次标为重点，
   并自动附带此前最多两分钟的有界参考上下文；`wish-ime.cmd mark` 与语言栏
   许愿仍冻结此前最多 30 秒。两条路径都
   最多保存 1024 条带单调时间的事件；
3. 绝对单调时钟不会进入包，每条事件只保存距离点击时刻的毫秒数；未带时间的
   兼容事件会明确计为省略，不会猜测；
4. 许愿快照在内存中形成严格有界的 `ziranma-wish-v8`，记录类别、重点事件范围、
   截取方式、每项候选的来源、实际已加载候选深度、当前页后已有候选/仍可继续
   加载/已到底、Tab 逐字组词位置与笔画前缀、可选的单音节/双音节自动换序决策，
   以及可用时的 DLL 与候选数据身份。持续研究开启时，主动许愿还记录同一进程内
   连续流的事件锚点，让独立分析器把重点现场连到对应自然片段；
   `ziranma-wish-v1/v2/v3/v4/v5/v6/v7` 继续兼容读取。随后立即由 Windows 当前用户
   DPAPI 保护，再通过只含密文的临时文件原子发布到
   `.local/tsf-alpha/user-data/wishes`；
5. “猫猫应愿”按时间列出本地包，并只为选中记录解密现场；说明侧车可以反复
   原子替换，原始包不变。`wish-ime.cmd mark` 只发送保存控制命令；保留的
   `start/stop/clear` 仅供开发
   生命周期检查。`status/list` 默认不解密；`show` 只有显式加入
   `--confirm-show-private-text` 才显示；`annotate` 把类别和留言另存为绑定同一
   随机内容 ID 的 DPAPI 文件；`trash` 需要确认并移动到可恢复目录；
6. 所有操作都不联网、不写模型、不读取光标周围正文，也不扫描既有私人会话。
   显式开启的持续研究复用相同事件格式和 DPAPI 边界，但写入独立的
   `research-inbox`，不会混进许愿列表。

明确保存动作会做一次有界 DPAPI 与本地写入，但它不是按键或候选刷新路径；失败
只形成脱敏状态，不会改变输入结果或停止反馈。当前 `wishpad` 已是按需打开的本地
管理器：列表只展示时间与整理状态，选择记录后显示类别、说明、截取方式和重点
事件；前后记录由用户再次展开。5 秒尾迹、截图、处理状态和批量筛选仍是后续工作，
复杂 UI 不驻留在每个 TSF 宿主中。

## 两层证据

默认诊断层不含文字，但仍属于私人行为元数据：

- Alpha 版本、DLL 摘要、候选包 revision 与反馈 schema；
- Windows 版本、DPI、主题、横/竖布局和当前页；
- 组合长度、候选数量、请求深度、缓存命中、视图类型；
- 每项已展示候选来自显式别名、项目词表、核心/补充词表、双字组合、普通解码、
  换序恢复还是找字模式，以及它是否被本次宿主会话的显式选择临时前移；来源与
  会话提升分开记录，临时前移不会覆盖原始来源；
- 解码、布局、窗口定位与绘制耗时；当前 Alpha 已在显式反馈开启时记录候选窗
  首个完整帧与完全可见耗时，立即显示模式下两者相同；
- 候选窗创建、显示、隐藏、移动、尺寸/圆角区域变化和重绘原因；
- 输入模式、焦点/组合生命周期、失败阶段与 HRESULT；
- 全部时间只保存相对反馈标记的单调时钟，不保存无关的长期活动时间线。

显式内容层可以额外包含：

- 反馈留言；
- 有效按键串、规范码、展示过的候选与实际提交；
- 用户主动选择的一张截图。

许愿的内容层由每次主动保存确认；持续研究则使用独立、默认关闭且可随时撤销的
持久授权标记。两者都不读取光标周围正文、剪贴板、窗口标题、文件路径或其他
输入法的按键。

## 进程与存储边界

TSF DLL 被加载进记事本、Codex 等宿主，不应在宿主 UI 线程里弹复杂窗口。当前
拆成两个角色：

- Alpha 维护有界内存环，在用户明确许愿时保存重点快照；若持续研究已显式开启，
  还会把不重叠日常事件批次 DPAPI 保护后原子写入独立收件箱；
- 独立前台 `wishpad` 只在用户打开后读取选中快照，并负责查看与整理说明。
- 独立 `researchctl` 按连续流重建自然片段并连接许愿；它可单独更新，不要求宿主
  卸载 TSF DLL。只有输入法内捕获字段变化才需要下一次安全换代。

保留的命令行控制层使用 TSF 当前用户全局 compartment，只传四种动作、一个有界
序号和脱敏确认状态。输入码、候选、留言、路径与快照都不进入 compartment；
每个宿主仍只在自身进程内冻结并使用 DPAPI 保存。管理器直接读取固定本地目录，
因此不需要为了预览新增跨进程明文管道。

## 前台入口的交互依据

- Windows Feedback Hub 把问题发生处的快捷捕获与“我的反馈/草稿”管理分开；
  Sentry User Feedback 也用持久入口捕获，再在类似邮箱的列表与详情页中处理。
  “猫猫应愿”因此不再重复输入法里的捕获按钮。
- Apple Feedback Assistant 允许先保留时效性现场，再补细节和管理状态；本项目借鉴
  这条顺序，但全部内容只留在当前用户本机。
- 管理器的视觉层级遵循 Fluent 的
  [字体](https://learn.microsoft.com/en-us/windows/apps/design/signature-experiences/typography)、
  [颜色](https://learn.microsoft.com/en-us/windows/apps/design/style/color)与
  [按钮](https://learn.microsoft.com/en-us/windows/apps/design/controls/buttons)原则：
  标题、正文和说明使用不同字重与字号，只让“整理这条记录…”成为强调按钮，
  状态和辅助说明降低视觉权重。颜色取自 Windows 系统角色，继续适配系统强调色
  与高对比度模式；原生 `BUTTON` 仍保留键盘焦点和无障碍名称。
- 独立管理器使用项目内生成的猫猫图标；多尺寸 ICO 被嵌入 `wishpad.exe`，其中
  “捧住愿望”小猫也作为轻量资源嵌入 TSF DLL，只用于明确保存成功后的短暂回执。
  图标来源、处理过程与尺寸清单见
  [`assets/wishpad/README.md`](../assets/wishpad/README.md)。

这些参考只决定入口层级：管理器仍是有界本地工具，不加入遥测、网络提交、自动
启动或驻留在 TSF 宿主里的复杂界面。持续研究也必须由独立设置显式开启。

新反馈包使用 `ziranma-wish-v8`，并兼容读取 `ziranma-wish-v1/v2/v3/v4/v5/v6/v7`，写入 Git 已忽略的
`.local/tsf-alpha/user-data/wishes/`。先在内存形成完整明文，再由 Windows 当前用户 DPAPI
保护，最后以“不覆盖既有文件”的原子发布方式保存；临时文件也只能包含密文。
任何解密、原文预览或导出都需要单独命令和明确提示。

## 必须保持的停止条件

- 默认滚动现场只存在于前台文本服务的有界内存中；只有明确许愿或独立开启持续
  研究才会写当前用户加密文件；
- 密码、PIN、`IS_PRIVATE`、键盘禁用、空 Context 和未知 InputScope 全部拒绝；
- 滚动模式达到事件或字节上限时淘汰最旧批次，并在快照中如实标记完整性；
- 伴随进程失败不能影响上屏、候选窗或宿主稳定性；
- 没有真实发布签名、管道威胁模型和恢复测试前，不随系统启动；
- 不把“保存到本机”与“发送给猫猫/GitHub”合并为一个动作。

## 实施顺序

1. 已完成候选窗首帧/完全显示耗时、重点片段 + 两分钟有界前情与显式 30 秒冻结、
   结构化 `ziranma-wish-v8`、V1–V7 兼容读取、逐候选来源、实际加载深度、
   分页余量（后续已加载/仍可加载/已到底）、Tab 组词位置/笔画前缀、会话提升标记与自动换序
   决策凭据、持续流位置与许愿锚点、DPAPI 原子写入、
   本地管理命令和无正文 TSF 控制通道；
2. 已完成按需打开的单实例“猫猫应愿”：时间列表、选中记录详情、重点/前后记录
   切换，以及可反复编辑的加密类别与说明；
3. 下一步根据真实使用决定处理状态、重要标记、搜索筛选和可恢复回收站入口，
   不先堆积空泛的后台功能；
4. 再增加可选尾迹、截图和逐项内容授权；
5. 最后才讨论跨宿主汇合或显式 GitHub 导出。

这条顺序让当前 Alpha 可以继续日用测试，同时不会为了“反馈更方便”把私人输入、
宿主稳定性和网络权限一次性混在一起。
