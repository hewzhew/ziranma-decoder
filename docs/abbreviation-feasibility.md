# 双拼与简拼融合的形式化可行性审计

## 结论先行

当前实现的“每个音节可任意选择一键简拼或两键完整双拼，并直接无分隔
拼接”在搜索工程上可以枚举，但在编码理论上**不是唯一可解码协议**。
这不是语言模型不够大或搜索不够快造成的：

- 固定公开 Rime 码本中的 26 个字母全都能作为一键简拼；
- 410 个不同的完整双拼码全都同时能切成两个一键简拼；
- 某些重复输入仅边界切法就按斐波那契数增长；
- 一键最多只有 `log2(26) = 4.70 bit`，而区分当前 411 个无声调拼音
  标签至少需要 `log2(411) = 8.68 bit`。

语言模型能够给这些解释排序，却不能消除编码本身丢掉的信息。自由混合
因此保留为压力测试和研究上界，不再默认是未来输入界面。近期应回到最初
目标：常用词快捷码、少数特殊缩写和更好的连续输入，并先选择一个歧义
受控的简写协议。

## 1. 被审计的协议

令 `P` 是无声调拼音音节集合，按键字母表为 `Σ`。自然码完整双拼把每个
音节映射为两个键：

```text
F: P → Σ²
```

当前一键简拼取完整码的第一键：

```text
A(p) = F(p) 的第一键
```

对音节序列 `p₁ … pₙ`，自由混合协议允许每个位置独立选择 `A(pᵢ)` 或
`F(pᵢ)`，然后不加分隔地连接。一个 `n` 音节词最多因此有 `2ⁿ` 种
拼写，键数在 `n` 到 `2n` 之间。

这里必须区分三个问题：

1. **可表示性**：搜索器能否产生某条一键/两键混合路径；
2. **唯一可解码性**：只看按键能否确定音节边界与音节标签；
3. **统计可用性**：有语言模型和候选选择时，正确文本能否以足够低的
   选择/改错成本出现。

现有 trie 和动态规划已经证明第 1 点在工程上可实现，但这不推出第 2
或第 3 点。

## 2. 非唯一可解码的直接证明

只要存在三个音节 `p, q, r` 满足：

```text
F(p) = A(q) · A(r)
```

同一个两键输入就至少有两种不同边界：

```text
[F(p)]       一个完整音节
[A(q)][A(r)] 两个简拼音节
```

公开码本审计发现 26 个字母全部能作为一键简拼，因此**每一个**有效完整
码的两个键也都是两个有效一键码。410/410 个完整码都有这种边界冲突。

一个不依赖兼容别名的具体反例：

```text
aa = 完整音节 a
aa = 简拼音节 a + a
```

这里的规范自然码 codec 使用 `an → an`，不是 `an → aj`；`aj` 只可能
来自某些实现派生的兼容输入，不能拿来证明宝宝实际布局有问题。上面的
`aa` 已足以构造“一个完整音节还是两个简拼音节”的长度不确定性。语言
自然度可以偏好其中一条，但罕见词、人名、专名和上下文不足时，按键本身
没有足够信息给出确定答案。

## 3. 歧义为什么会指数增长

公开码本同时含有一键码 `a` 和两键完整码 `aa`。对只由 `a` 组成的长度
`n` 输入，第一段可以取一键或两键，因此边界解释数满足：

```text
T(0) = 1
T(1) = 1
T(n) = T(n-1) + T(n-2)
```

即 `T(n) = Fibonacci(n+1)`：

| 输入长度 | 仅一键/两键边界解释数 |
|---:|---:|
| 8 | 34 |
| 16 | 1,597 |
| 32 | 3,524,578 |

这些数字还没有乘上每个一键背后的拼音标签、汉字候选、词界和纠错路径。
实际公开码本中：

- 411 个不同拼音标签映射到 410 个完整码；
- 26/26 个一键都对应多个拼音标签；
- 一个一键最多对应 26 个拼音标签；
- 两键 `ll` 在“一个完整音节”与“两枚简拼音节标签组合”之间共有
  677 条拼音标签路径。

动态规划可以合并相同未来状态，控制运行时间；它不能恢复已经丢失的
信息，也不能保证正确文本排到可见候选中。此前全简拼公开答案
Top-10 为 0，正是这种结构风险的一个观测，而不是本证明的前提。

## 4. 为什么一键必然需要外部信息

一个字母键最多携带：

```text
log2(26) = 4.70 bit
```

在当前公开码本的 411 个拼音标签中选择一个，至少需要：

```text
log2(411) = 8.68 bit
```

所以一键简拼不可能独立标识一个拼音音节。缺少的约 4 bit 必须来自：

- 已知词语或快捷码词典；
- 前后中文上下文；
- 明确的简拼模式或边界标记；
- 用户从候选栏进行的确认；
- 个人历史和当前应用上下文。

这不表示“一键快捷输入绝对不可用”，而是表示它应被建模为**预测或
快捷码**，而不是与完整双拼地位相同、可在任意位置自由切换的无损编码。

## 5. 候选协议比较

| 协议 | `n` 音节的拼写规模 | 边界性质 | 近期判断 |
|---|---:|---|---|
| 每音节自由一键/两键 | `2ⁿ` | 非唯一；存在指数边界歧义 | 降为压力测试 |
| 每个词最多省略一次第二键 | `n+1` | 仍非唯一，但歧义有界 | 可作保守实验 |
| 完整码锚定后，仅允许尾部连续简拼 | `n+1` | 只有一个“切换点”隐变量 | 值得验证 |
| 一个词要么全完整、要么全首键 | 每词 2 种 | 词界仍隐含，但不任意交错 | 值得验证 |
| 常用词/短语显式快捷码白名单 | 由白名单限制 | 冲突可离线审计 | 最贴近原始目标 |
| 显式简拼模式或边界标记 | 边界确定 | 牺牲一次模式/标记操作 | 最可控 |
| 把简拼视为候选补全 | 不是完整编码 | 用户选择提供缺失信息 | 实用优先路线 |

### 推荐的近期组合

1. 完整双拼与现有一次按键容错继续作为可靠主路径；
2. 第一种简写实验改为“常用词/短语快捷码白名单”，不允许任意音节混合；
3. 第二种实验比较“完整前缀 + 连续尾部简拼”，要求至少一个完整音节
   作为锚点；
4. 锚定尾部简写只把一次相邻颠倒放入独立恢复候选栏；其他简写纠错
   暂不与主榜混排，避免两个信息损失通道相乘；
5. 所有简写只生成候选，永不静默上屏；
6. 自由混合继续留在回归测试里，用来检验搜索器完整性和最坏情况。

这组选择把项目重新对准最初诉求：常用表达少按几键、词与词之间更容易
连打，而不是要求任意长输入都能从任意首字母序列中唯一恢复。

## 6. 进入下一轮实现前的决策门槛

任何新简写协议必须先通过以下非模型门槛：

- 候选拼写数随音节数至多多项式增长，或由显式白名单给出硬上限；
- 能写出确定的边界状态和冲突检测规则；
- 完整双拼路径永远保留，未知按键仍原样显示；
- 简写节省的键数要大于候选选择、翻页与改错的期望成本；
- 先在 2～4 词短语上报告 Top-K、平均排名和净按键节省；
- 不允许用长句语言模型掩盖短语协议本身的结构缺陷；
- 若受限协议在独立调参集上仍不能稳定进入可见候选，就停止该分支。

模型路线暂时排在协议选择之后。只有受限协议本身通过上述门槛，才继续
比较字符模型、词模型和输出长度先验。

## 7. 可复核命令

```powershell
cargo run --release -- abbreviation-audit
```

命令只读取固定公开 Rime 快照，报告本页使用的码本计数、直接反例和
斐波那契边界数。它用于核对实际自然码码本是否满足证明条件；证明本身
不依赖某次准确率实验。
