# Codex 专用持续记录器

## 目标与当前边界

`codex-recorder` 把已经人工验证过的单框探针扩成一个可长时间运行的
**Codex 专用、本地、增量记录器**。它解决的是“必须想起来才开一次探针，
自然样本永远很少”的问题，不把范围扩成整台电脑的通用键盘记录器。

当前版本：

- 自动发现名称精确为“随心输入”的可编辑、非密码 UIA 元素；
- 还要求 `FrameworkId=Chrome`，并且控制树上存在名称精确为 `Codex`
  的文档祖先；
- 若同时存在多个合格元素，只接受其中唯一持有焦点的一个，否则等待而
  不是猜选；
- 焦点变化使用 UIA 的运行时元素身份比较，不把同一进程里的同名框当成
  已绑定目标；
- Codex 退出或 UIA 元素被重建后自动解除旧监听并等待；新目标再次唯一
  出现时自动重连，不依赖旧 PID；
- 若元素恰好在“发现目标—注册监听—二次读取基线”之间重建，记录器会
  回滚已注册的监听、关闭空的 continuity 边界并继续等待，而不会把这次
  UIA 瞬时失效当成整个长期会话的致命错误；
- 发送消息或切换任务引起的短暂元素重建会合并显示为一条 `REBOUND`；
  重建前的非空事件先刷新，新编辑框的既有文字只作内存基线，不会重复
  保存。只有超过两秒仍找不到目标时才显示 `WAITING`；
- 只在精确目标持有焦点时捕获受限按键；候选窗暂时取焦时，只在该目标
  已经开始的活跃组合内延续；
- 主线程使用 Windows 消息等待：热键或队列消息会立即唤醒；空闲时最多
  每 250 ms 才为有界轮询醒来，不再以 25 ms 周期主动忙等；
- 已连接时的周期体检只验证旧元素存活，并在当前焦点恰好是另一个精确
  Codex 编辑框时比较运行时身份；只有断开等待期间才扫描后代寻找目标，
  避免每秒遍历整个桌面 UIA 树；
- 不读取其他应用的文字，不保存输入框原有全文，不截图、不读剪贴板、
  不联网，也不安装系统自启动。

Codex 的旧版本曾把目标 class 暴露为 `ProseMirror`，当前版本已经改变。
class 现只出现在脱敏体检计数中，不作为长期硬条件；目标名称、控件安全
属性、Chrome 框架、Codex 文档祖先和运行时元素身份仍全部保留。

## 先做只读体检

这个命令不安装监听、不读取输入值、不建目录、不写文件：

```powershell
Set-Location -LiteralPath 'C:\path\to\ziranma-decoder'
cargo run --bin codex-recorder -- --check
```

正常情况下应看到：

```text
CODEX_RECORDER_CHECK candidates=1 ... disk_writes=false listeners=false
```

中间的计数只说明目标规则在哪一层剩下多少元素，不包含控件内容。若
`candidates=0`，记录器的运行模式会保持等待；不要为了“让它工作”而
随意删除非密码、框架或 Codex 祖先检查。

## 启动一次长期会话

建议先构建 release：

```powershell
cargo build --release --bin codex-recorder
.\target\release\codex-recorder.exe --run
```

默认会话类别为 `daily`，每 128 个原子事件或有待写事件经过 60 秒时
轮换一个加密段，以先到者为准。可以显式改变有界参数：

```powershell
.\target\release\codex-recorder.exe --run `
  --session-kind daily `
  --segment-events 128 `
  --flush-seconds 60
```

`--segment-events` 只接受 1–512；`--flush-seconds` 只接受 5–900。
终端输出只含连接状态、数量和加密段大小，不显示文字、拼音、具体按键或
本地路径；分段回执固定声明 `path_disclosed=false`。这些会话号、数量、
刷新时刻和连接变化仍是行为元数据，不能因为没有正文就当作匿名数据。
终端可以最小化，但当前没有托盘图标；进程退出后也不会自行重启。

经 `recorderctl run` 启动且当前构建声明支持时，控制器会附加
`--control-state`。这不是采集日志：记录器只把会话号、PID、类别、版本、
开始时间、连接/暂停状态、已完成分段/事件数和最近刷新时间写到 Git 忽略
的 `.local/recorder/active-v1.txt`。固定文件不含正文、拼音或按键，只在
生命周期变化或非空加密分段完成时原子替换，没有每秒心跳。直接运行
`codex-recorder --run` 默认仍不写这份控制状态。

控制热键：

- `Ctrl+Shift+F10`：暂停；立即加密并刷新已有事件。
- 再按 `Ctrl+Shift+F10`：恢复；重新读取当前输入框作为内存基线，暂停
  期间输入的文字不会补录。
- `Ctrl+Shift+F12`：停止；刷新最后一个非空段并移除监听。

启动后不再需要旧探针的 READY 步骤。记录器注册监听时先保持 disarmed，
随后在进程内管线锁内重新读取当前字段作为基线、安装限域按键会话，再
原子启用回调；注册窗口内的已有草稿或变更不会作为事件保存。由于 Windows
不能提供跨键盘钩子与 UIA 的原子系统快照，每次连接或从暂停恢复后的第一
条实际记录仍保守标成 `keys_complete=false`，不会把极窄 setup gap 伪装
成完整证据。

## 现在究竟保存了什么

每个加密段包含会话号、段序、开始/结束时间、会话类别、记录器版本和
采集口径，以及一组按段内相对时间排序的原子事件。提交事件保存：

- 限域后的字母、数字、选词、删除与导航等逻辑按键，以及按键是否完整；
- 最终一次输入法组合串；
- 组合区从拼音到上屏文字的起点、删除串、插入串和位置证据；
- 整个编辑框在本次提交前后的文档净差分，使用同一组字段。

普通修订事件保存限域按键、完整性和文档净差分。记录器不周期保存输入框
全文；启动、恢复或重连时已有的文字只作内存基线。不过，连续的插入和
删除差分本身往往足以还原宝宝实际输入过的正文，大段清空也可能把整段
旧文字放进 `deleted`，所以 `.zcs` 仍应按完整私人内容保护，不能把“差分”
误解成脱敏。

`codex-uia-v2` 还在同一份 DPAPI 密文里加入
`ziranma-codex-uia-integrity-v1` 完整性块。它只聚合已经通过上述 Codex
目标门控的管线证据：tracker 基线代数、粗粒度切段原因、交给 tracker 的
受限按键数、组合/值/组合结束回调数、值/组合/选择读取失败数、没有形成
Commit/Revision 的值回调数、边界处未进入记录的待配对按键数，以及 128
键保护缓冲被重置的次数。实际输出数同时写入并与 capsule 事件数作硬校验。
这些数字表示“记录器观察到了什么”，不能证明 Windows 或 UIA 上游绝无
漏报。

回调计数与它产生的可选 TrackerOutput 通过同一条进程内管线原子交给段
写入器。暂停或目标断开会先拒绝新回调，再等待已经进入管线的回调完成，
最后吸收边界计数并关闭该基线；`continuity` 之后必须建立新的 baseline
epoch 才能继续写，`session-end` 之后则永久拒绝本会话的新事件。这样段
边界既不会切开一条回调，也不会把恢复后的事件悄悄写回旧基线。

当前没有保存输入法候选列表或名次、逐次中间组合状态、每条提交各自的
组合更新数、精确选择端点、逐键按下/抬起与停留时长、鼠标/剪贴板/截图、
IME 配置或自定义短语来源，也没有保存“打错字、改写措辞、查生僻字”等
意图标签。其他应用和暂停期间的输入不在采集范围内。

### 完整性 v2 与后续分层

第一层已经以 v2 实现，但刻意保持低分辨率：暂停、目标消失和 DOM/任务
重建统一记为 `continuity`，不在密文中细分用户行为；没有 TrackerOutput
的区间不单独制造空段。若一个已有事件的段同时经历读取失败或未完成组合，
对应计数会随该段原子保存；若整个基线区间从未形成事件，边界处只丢弃
内存计数。这一限制避免仅因打开、暂停或切换任务就额外留下可见文件节奏，
健康报告会明确说明 v1 是“无完整性证据”，而不是把缺失当作零。

真正的落盘失败也不能诚实地写进“正是因为失败而没能写成”的那个段；
记录器继续 fail closed，并由无正文的生命周期状态和固定终端错误表示，
不伪造 `storage_failures=0`。Caret 是否参与定位、Commit/Revision 数、
`keys_complete=false` 和逻辑按键数已经能从 capsule 机械推导，因此没有在
完整性块中重复存一份。

第二层只保存粗化值，例如组合总时长、文档/选择长度分桶、选择动作类别、
焦点和重连次数；不保存逐键时序或精确端点。第三层才面向显式、短时的
`course` / `theme` 实验，单独确认后可研究候选 Top-K 文字/名次/页码、
中间组合状态、精确选择、本地上下文、IME 模式和自定义短语来源。第三层
必须使用新的 `capture_profile`、有界时长与独立升级流程，不能静默混入
长期 `daily` 会话。

周期性全文快照、整个可访问性树、全局键盘、剪贴板、截图、其他应用正文、
明文日志和网络上传继续列为禁区。采集口径一旦改变，旧会话只能作为旧
profile 的历史，不能与新版数字无标记混算。

## 加密增量段

文件只写到：

```text
data/private/continuous-capture/segment-<会话号>-<序号>.zcs
```

会话号由启动毫秒时间和记录器 PID 组成，只用于新文件名和顺序，不包含
输入文字。`daily`、`course`、`theme` 类别写在加密载荷内，不出现在
文件名；它们是以后做日常、课程式和主题式对照的标签骨架，当前不改变
捕获内容或模型。

同一加密载荷还包含 `producer_version` 与 `capture_profile`。前者区分
实现修订，后者冻结按键限域、组合归并和差分的语义口径。回放器拒绝未知
profile，避免把不同采集含义的数字直接相加。

新记录器先在内存中生成严格的 `ziranma-continuous-segment-v2`；其中仍
复用 `ziranma-event-capsule-v1` 原子事件，只新增完整性块。旧的
`ziranma-continuous-segment-v1` / `codex-uia-v1` 文件不迁移、不重写，
新版回放器按 schema 分派并同时支持两代；schema 与 capture profile 不
匹配时安全拒绝。v1 缺少的完整性字段永远解释为 unavailable，不是 0。

随后整个连续段使用 Windows DPAPI 的**当前用户**作用域保护。实现没有设置
`CRYPTPROTECT_LOCAL_MACHINE`，并使用 `CRYPTPROTECT_UI_FORBIDDEN`
禁止后台弹出凭据界面。只有保护成功后的不透明字节才会进入同目录临时
文件；刷新并同步后，用拒绝覆盖的最终名称发布。临时文件也已经加密，
磁盘上没有明文阶段。

这个保护意味着通常只有同一台电脑上的同一 Windows 登录账户能解密。
它不是跨机器备份格式；管理员重置账户密码等情况也可能使旧数据不可恢复。
系统内存并不是安全隔离区：捕获、差分和回放期间仍会短暂存在私人明文。

已完成的段不会因下一次崩溃被追加或截断。异常退出最多损失当前尚未轮换
的内存段，默认边界为 60 秒或 128 个事件；正常暂停、停止和 Codex 断开
都会主动刷新。极窄的“加密临时文件已经同步、最终名称尚未发布”崩溃
窗口，或最终名称发布后清理临时别名失败，都可能留下隐藏的加密临时
文件；它仍是 DPAPI 密文，当前不会自动扫描或猜测恢复它。

## 只读回放

回放要求点名文件或会话号，不扫描私有目录。`.zcs` 会在内存中按当前
Windows 用户解密，然后走与 `.zic` 相同的脱敏聚合路径：

```powershell
cargo run --release --bin capsule-replay -- `
  --input data/private/continuous-capture/segment-<会话号>-00000000.zcs `
  --window-gap-ms 15000 `
  --compact
```

多个段可重复给出 `--input`；过去/未来个人缓存实验也可把 `.zcs` 用在
`--history-input`。命令不导出解密明文、不改原文件，终端报告不包含
文字。回放按显式顺序一次只打开、解密、解析并聚合一个段，随后释放该段
的原子事件；整次会话不再同时驻留内存。个人缓存模式仍会保留因果学习
需要的词频、词对和当前报告聚合。这里的“流式”只描述明文事件的内存
生命周期，不改变实验语义：段边界仍是胶囊边界，跨恰好一个轮换点的
连续窗口不会被强行拼接。若真实数据表明这个边界影响评测，必须另行设计
显式的跨段窗口口径，不能借内存优化默默合并。

DPAPI 解密得到的字节缓冲区在解析后会主动覆零；解析形成的 Rust 字符串、
解码器临时值和个人缓存则按普通对象生命周期释放，并不承诺密码学意义的
内存擦除。因此这项优化减少了同时存在的私人明文量，但不能宣称进程内存
从未出现明文或已被可靠清零。

成功报告只含聚合计数；selector 展开、载入与分析失败按所在阶段至多显示
历史/评测组、输入序号及不含内容的通用类别。命令行、PowerShell 历史和
进程列表仍会看到操作者显式给出的路径或会话号，因此私人文件名不应写入
正文或敏感主题。

正常停止还会打印一条 `CODEX_RECORDER_FEEDBACK` 和可直接复制的
`FEEDBACK_COMMAND`。后者使用显式 `--session <会话号>`，按连续段序号
展开这一轮而不扫描目录：

```powershell
cargo run --release --bin capsule-replay -- `
  --session <会话号> `
  --window-gap-ms 15000 `
  --compact
```

长会话中途只想确认采集健康时，可使用不运行候选解码器的轻量模式：

```powershell
cargo run --release --bin capsule-replay -- `
  --session <会话号> `
  --health-only
```

它通常只需读取已经完成的段。第一行 `CAPTURE_HEALTH` 输出提交、修订、
按键完整性、组合内编辑键、修订形状和位置歧义等既有脱敏计数；第二行
`CAPTURE_INTEGRITY` 只对 v2 段聚合上述管线证据，并单列
`legacy_inputs_without_integrity`。第二行显式标记
`contains_behavioral_metadata=true`；第一行现在也带同一标记，因为提交、
修订、逻辑按键和编辑形态同样属于行为元数据。两行分别使用独立的
`report_schema`，第二行另以 `integrity_schema` 标明密文载荷口径。它们不
打印逐段 epoch、时间、路径、profile 或错误码。
尚在内存中的当前段仍不会进入快照。

完整回放也只在一次原子提交内复用相同码串的候选结果，并把逐提交阶段
已经得到的规范分词直接交给连续窗口阶段。这个缓存不跨提交、不跨胶囊、
不写磁盘，也不成为个人模型；优化前后报告必须逐字一致。

怎样让旧会话只学习、下一次独立会话只考试，以及什么时候接受、回退或
停止一次升级，见[反馈驱动升级闭环](feedback-upgrade-loop.md)。

## 尚未自动做的事

- 没有写入 Windows 启动项、计划任务或 Startup 文件夹。
- 没有托盘图标、自动更新、自动删除和保留期限。
- 没有跨应用捕获，也没有“所有 Chrome 输入框”模式。
- `course` / `theme` 目前只是加密会话类别，没有动态标题、课程步骤或
  主题提示；这些应叠加在同一事件流上，而不是另造一套采集器。
- 没有把私人历史自动训练成可持久化模型。先收集独立会话，再用严格的
  过去/未来回放验证它是否真的帮助。

若宝宝确认手动长期会话稳定，下一次再单独决定是否创建一个**可见、可
卸载**的登录启动入口。安装启动项属于系统状态修改，不能因为编译完成就
偷偷执行。
