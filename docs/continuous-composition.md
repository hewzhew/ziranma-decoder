# 连续组合与顺序颠倒恢复

## 用户目标

输入法不应要求每打完一个词就按空格确认。以“麻烦猫猫”为例：

```text
完整双拼：mafj + mkmk = mafjmkmk
尾部简写：maf  + mkm  = mafmkm
```

`maf` 保留“麻”的完整音节 `ma`，只省略“烦”的第二键；`mkm` 同样
保留第一只“猫”的完整码 `mk`，第二只“猫”只输入 `m`。两个词之间
没有分隔键，句子搜索器自行寻找 `maf | mkm`。

## 当前结果

固定 Rime 公开词典中：

- `mafmkm` 的主候选第一是“麻烦猫猫”；
- 自动词界为 `maf | mkm`；
- 两个词都被解释为“第一音节完整、第二音节简写”；
- 完整码需要 8 个字母，连续尾部简写需要 6 个字母。

如果把第一组 `mk` 相邻打反：

```text
预期：mkm
实按：kmm
整段：mafkmm
```

单词搜索能把 `kmm` 解释为 `mkm`，并明确报告一次 `mk → km` 相邻
颠倒。问题不在纠错生成，而在普通句子列表把所有零错误简拼组合绝对
排在纠错路径之前。

## 为什么使用候选分栏

完全取消“零错误优先”会让高频纠错词压过干净输入：小型回归集的短句、
长句 Top-1 都会退化。因此当前不改变稳定主榜，而是分别保留：

1. 主候选：零错误优先，维持现有干净输入行为；
2. 恢复候选：所有词均为完整码或“完整首音节 + 连续尾部简写”，并且
   恰有一处简写词内部的相邻颠倒。

内部 k-best、词条终点和句子转移都分别保留普通候选与锚定颠倒候选，
避免恢复路径在动态规划中提前消失。交互视图使用至少 20 条内部前沿
寻找恢复证据，但每栏只展示调用者要求的少量候选。

这不是要求用户切换模式。未来界面可以把恢复候选占用一个首屏保留位，
或在候选旁显示轻量的“顺序颠倒”标记。

## 可复核命令

```powershell
cargo run -- public-sentence mafmkm 10
cargo run -- public-compose mafkmm 3
cargo run --release -- public-compose-evaluate
cargo run --release -- public-compose-audit
```

第一条检查干净连续输入；第二条同时显示稳定主候选与相邻颠倒恢复栏。
后两条分别运行固定短语评测和首屏外失败审计。

## 固定公开短语评测

`public-compose-evaluate` 从固定 UD Chinese GSDSimp test 中检查相邻
两个非标点 token，只保留：

- 合计 2～6 个纯汉字；
- 两个 token 都作为完整词存在于固定 Rime 词典；
- 尾部简写至少省一键；
- 某个多音节词的首音节两键不同，可以构造相邻颠倒。

9,819 个双词窗口中，8,891 个长度与字符合格，7,465 个整词可覆盖，
5,919 个能省键，5,796 个能构造颠倒。最初采用“源序前 64 个窗口”时，
样本高度重叠，失败项全部集中在 test 前 6 句，独立信息被严重高估。

现行选择先让每个源句至多贡献一个唯一窗口，得到 489 个独立句代表；
再按来源位置等距取 64 条，选择过程不读取任何解码结果。结果为：

| 轨道 | Top-1 | Top-3 | Top-5 | Top-10 |
|---|---:|---:|---:|---:|
| 完整码主榜 | 39/64 | 53/64 | 57/64 | 61/64 |
| 尾部简写主榜 | 18/64 | 31/64 | 37/64 | 40/64 |
| 尾部简写主榜 Top-10 内同字数 | 19/64 | 31/64 | 37/64 | 40/64 |
| 颠倒输入主榜 | 0/64 | 0/64 | 0/64 | 1/64 |
| 锚定颠倒恢复栏 | 18/64 | 35/64 | 36/64 | 40/64 |

完整码共 418 键，尾部简写共 337 键，少 81 键（19.4%）。尾部简写中
18 条直接首选，另有 22 条位于第 2～10，24 条仍在 Top-10 外。若首屏
非首选各乐观地只计一次选择，已省 81 键对应 22 次额外选择；Top-10
外的 24 条成本未知，不能冒充净节省。

## 首屏外失败审计

`public-compose-audit` 保持主榜 Top-10 不变，只为 24 条失败样本另取
普通 unigram Top-100，并冻结这一个候选池：

- 16 条答案位于第 11～100，8 条仍在 Top-100 外；
- 24 条错误 Top-1 全部与答案同字数；
- train-only 词级 bigram 重排冻结池后，5 条回到 Top-10，仅 1 条第一；
- 纯字符平均 bigram 让 4 条回到 Top-10，没有一条第一。

所以问题并非主要来自一字/多字候选挤占。搜索已经能表示每条预期路径，
但有 8 条在现行 unigram 下排到一百名以后；对于已经进入池的 16 条，
现有 train-only 上下文也远不足以稳定修复。评测因此明确拒绝了“直接
接入当前 bigram 就会变好”这个诱人的工程捷径。

## 下一步

下一轮应先从公开 train 内部切出不参与训练的 dev，比较更强但仍可审计
的上下文特征；固定 test 不再参与模型选择。只有 dev 明确改善同长度
排序且不伤害干净输入，才进入生产候选。随后再为同一批短语加入邻键
替换、漏键和多按，并按真实候选位置计算选择成本。
